## Brief statements that need re-checking

- The brief lists `GET /users/{id}` and a per-user `get_sign_in_activity(user_id)`. If A-01 and A-03 hold, a single paginated `GET /v1.0/users?$select=…,signInActivity` is enough, and the per-user operation is **not** added to the Phase 1 manifest. Fewer allowed operations means a smaller boundary.
- The brief's isolation section says "separate process or container". The design commits to containers, because a plain host process cannot be denied network egress portably (threat-model §7).

## Task 17B verification findings (checked 2026-10-20)

All sources are Microsoft Learn. Checked 2026-10-20. "Impact" says whether the implementation already matches and whether a code change was made. Nothing here was tested against a live tenant or live Graph.

- **F-A01 — verified (docs).** *List users* (v1.0): "Details for the **signInActivity** property require a Microsoft Entra ID P1 or P2 license and the `AuditLog.Read.All` permission." Listing `/users` (app-only) uses `User.Read.All` (or `Directory.Read.All`); no write permission is involved. The profile `directory-read-auditlog-read` expects exactly `{AuditLog.Read.All, User.Read.All}`. **Impact:** matches; no change. Source: https://learn.microsoft.com/en-us/graph/api/user-list?view=graph-rest-1.0 (updated 2026-05-14).
- **F-A02 — partial (docs).** The P1/P2 requirement is documented (*Manage inactive user accounts*: "To access the `lastSuccessfulSignInDateTime` property using Microsoft Graph, you need a Microsoft Entra ID P1 or P2 license"; also the *List users* note). The **exact 403 status and the error code `Authentication_RequestFromNonPremiumTenantOrB2CTenant` are NOT in official Microsoft docs** — only community posts. **Unresolved; needs a real-tenant test.** **Impact:** no change — the transport maps that code to `licence_required` as a best-effort legacy mapping; any other 403 maps to `forbidden` (fail closed), so the undocumented code is not relied on for safety. Sources: https://learn.microsoft.com/en-us/entra/identity/monitoring-health/howto-manage-inactive-user-accounts (updated 2026-05-05); https://learn.microsoft.com/en-us/graph/api/user-list?view=graph-rest-1.0 .
- **F-A03 — verified (docs).** *signInActivity resource type* (v1.0) lists `lastSignInDateTime`, `lastNonInteractiveSignInDateTime`, `lastSuccessfulSignInDateTime` (and their request-id siblings) on **v1.0**. **Impact:** matches (operation pinned to v1.0; classifier uses these). No change. Source: https://learn.microsoft.com/en-us/graph/api/resources/signinactivity?view=graph-rest-1.0 (updated 2025-07-05; ms.date 2024-07-22).
- **F-A04 — wrong (corrected).** *List users* (v1.0): "When you specify `$select=signInActivity` or `$filter=signInActivity` when listing users, the maximum page size for `$top` is 500. Requests with `$top` set higher than 500 return pages with up to 500 users." The registry bounded `$top` at 999. **Code change:** `src/clw/broker/operations.py` `_MAX_TOP` 999 to **500** (this operation always selects signInActivity). Not a security hole before (Graph silently caps), but the bound now reflects the documented maximum. Regression tests updated in `tests/security/test_operations.py` (plus the stage-2/binding cases in `test_policy.py` and `test_broker_ops.py` that used 999). Source: https://learn.microsoft.com/en-us/graph/api/user-list?view=graph-rest-1.0 .
- **F-A05 — verified (docs), informational.** *Manage inactive user accounts*: "[Reports Reader] is the least privileged role required to access the activity logs." Relevant only to the delegated design (SD-010), which is not built in Phase 1. **Impact:** none. Source: https://learn.microsoft.com/en-us/entra/identity/monitoring-health/howto-manage-inactive-user-accounts .
- **F-A06 — verified (docs).** *Access token claims reference*: `roles` — "The client credential flow uses this set of permission in place of user scopes for application tokens"; `scp` — "Only included for user tokens." *Optional claims reference*: `idtyp` is `app` for app-only tokens and, by default, emitted only for app-only tokens. **Impact:** matches the validator (`idtyp == app`, or `roles` present and `scp` absent). No change. Sources: https://learn.microsoft.com/en-us/entra/identity-platform/access-token-claims-reference (updated 2026-07-24); https://learn.microsoft.com/en-us/entra/identity-platform/optional-claims-reference .
- **F-A07 — verified (docs).** *Access token claims reference*: `aud` "must be validated, reject the token if the value doesn't match the intended audience"; access tokens are issued for the resource (the audience). Microsoft's token-validation guidance is that only the intended audience validates the signature; a client should not validate access tokens it is not the audience for. The broker inspects claims (`tid`, `appid`/`azp`, `aud == Graph origin`, `roles`) of a token received directly from Entra over TLS and does not verify the signature (SD-004 limit). **Impact:** matches; no change. Sources: https://learn.microsoft.com/en-us/entra/identity-platform/access-token-claims-reference ; https://learn.microsoft.com/en-us/entra/identity-platform/claims-validation .
- **F-A08 — verified (docs).** *Access token claims reference*: `appid` "only present in v1.0 tokens"; `azp` "a replacement for `appid` ... only present in v2.0 tokens"; `iss` ends in `/v2.0` for v2.0 tokens (v1.0 uses `https://sts.windows.net/{tid}/`); `ver` is `1.0` or `2.0`. The validator accepts **either** `appid` or `azp` and checks `aud`, so it is correct whichever format Graph emits; it does not pin the issuer (recorded SD-004 limit). **Impact:** matches; no change. Source: https://learn.microsoft.com/en-us/entra/identity-platform/access-token-claims-reference .
- **F-A09 — partial (docs).** Tokens have a limited lifetime and MSAL caches in memory; a new app-only token carries the then-current `roles`. The exact consent-propagation delay is not a single documented number. **Unresolved timing; needs a tenant test.** **Impact:** none — the validator re-checks `roles` against the expected set on every acquired token and refuses over-consent (`permissions_extra`), so stale caching fails closed. Source: https://learn.microsoft.com/en-us/entra/identity-platform/access-tokens .
- **F-A10 — verified (docs), with a caveat.** *Client credentials (MSAL Python)*: the `client_credential={"private_key","thumbprint"}` PEM form is supported, but "support using a certificate in X.509 (.pem) format is deprecated because it uses SHA-1 thumbprint"; PFX (SHA-256) is preferred, and since 1.35.0 `public_certificate` without a thumbprint auto-computes an SHA-256 thumbprint. Certificate client credentials work for multi-tenant apps. **Impact:** the current design works and is not a security defect (the thumbprint is a key-selection identifier, not a security primitive). Migrating off the SHA-1 thumbprint form is a **design decision for a later task**, not a 17B correction. Sources: https://learn.microsoft.com/en-us/entra/msal/python/advanced/client-credentials ; https://learn.microsoft.com/en-us/python/api/msal/msal.application.confidentialclientapplication?view=msal-py-latest .

No change. Sources: https://learn.microsoft.com/en-us/entra/identity-platform/id-tokens ; https://learn.microsoft.com/en-us/entra/identity-platform/v2-protocols-oidc .
