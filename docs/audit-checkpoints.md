# Audit checkpoints: making tampering detectable by someone other than the host

**The limit first.** The audit trail is a hash chain in Postgres. On its own it catches a record that was changed or deleted, but **not a consistent rewrite**:
- whoever controls the host or the database (a DBA, a superuser, an attacker with either) can rewrite the chain from any point to the end, recompute every hash, and the chain verifies as valid again;
- they can also cut off the most recent records.

A test pins this down (`test_superuser_full_rewrite_is_not_detected_by_verifier_alone`, SD-006).

**Checkpoints close that gap up to the last checkpoint.** A checkpoint is a small signed file. It fixes the chain's exact contents up to a point: a fingerprint of every record, the head hash and the record count, signed with an Ed25519 key. A later rewrite of anything it covers no longer matches.

That only helps if **the signing key and the checkpoint files are somewhere the host and the DBA can't write.** A checkpoint kept on the same host can be deleted or regenerated by the same person who rewrote the chain.

**v0.1 doesn't schedule checkpoints or store them off-host.** Running them, and choosing where they go, is up to you, as described below. Built-in scheduled off-host checkpoints are tracked as a priority issue.

## 1. Create the signing key, off the host

On a machine the Cloud Locksmith host can't reach (your laptop, a secrets manager, a hardware key's host):

```sh
uv run python -m clw.cli audit-keygen --private checkpoint-signing.pem --public checkpoint-verify.pem
```

- **`checkpoint-signing.pem`** is the private key. It never goes on the Cloud Locksmith host or into its database.
- **`checkpoint-verify.pem`** is public. Anyone may hold it to verify checkpoints.

## 2. Take a checkpoint

The chain ID is the tenant ID. Run this wherever the signing key is, with a database role that can read `audit_events` (it needs nothing else):

```sh
export DATABASE_URL='postgresql+asyncpg://<read-only user>:<password>@<host>:<port>/<db>'
export CLW_AUDIT_CHECKPOINT_KEY_PATH=./checkpoint-signing.pem
uv run python -m clw.cli audit-checkpoint --chain <tenant-id> --out ./checkpoints
```

It writes `./checkpoints/<tenant-id>-<last seq>.json` and never overwrites an earlier file.

- **The chain is invalid:** the command refuses (exit code 1). To keep signed evidence of what you saw, add `--allow-invalid`; that checkpoint is labelled `INVALID` and never verifies as ok.
- **The database is unreachable:** add `--record-unavailable` to sign that fact instead (status `UNAVAILABLE`).

## 3. Store it where the host can't write

Copy each checkpoint file to storage the host and the DBA can't modify or delete:
- object storage with a retention lock (for example S3 Object Lock in compliance mode, or an Azure Blob immutability policy);
- a separate system with its own administrators;
- at the very least, a machine and account that are not the Cloud Locksmith host's.

## 4. Verify later

Anyone with the public key can check that the chain still matches a checkpoint:

```sh
export CLW_AUDIT_CHECKPOINT_PUBKEY_PATH=./checkpoint-verify.pem
uv run python -m clw.cli audit-verify-checkpoint --chain <tenant-id> --checkpoint ./checkpoints/<file>.json
uv run python -m clw.cli audit-verify --chain <tenant-id>
```

Exit code 0 means the chain still matches the checkpoint and verifies end to end. Exit code 1 means it doesn't.

## How often

**Everything after the last checkpoint can still be rewritten or cut off undetected.** That window is your exposure, so take checkpoints at least daily, and after anything you'd want to prove later: a session you care about, an incident, a proposal. Until scheduling is built in, a scheduled job on the off-host machine (cron, Task Scheduler, a CI schedule) running step 2 and then step 3 is the practical setup.

Details of the format and its tests are in [security-decisions.md](security-decisions.md), SD-006. Recovering a broken chain is covered in [runbooks/audit-chain-recovery.md](runbooks/audit-chain-recovery.md).
